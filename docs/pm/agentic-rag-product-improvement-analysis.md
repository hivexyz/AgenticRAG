# AgenticRAG 产品改进分析

日期：2026-06-14
角色视角：AI 产品经理

## 一句话判断

当前项目已经具备一个 **Agentic RAG 技术原型** 的核心能力：文档入库、多格式解析、文本切分、Embedding、向量检索、可选 Rerank、答案生成、质量评估、Gradio 前端和多租户能力。

但如果要从“可运行 Demo”走向“可被真实用户持续使用的 AI 产品”，它还需要从以下几个方面升级：

1. 明确用户场景；
2. 强化可信答案体验；
3. 完善文档生命周期管理；
4. 建立用户反馈与评估闭环；
5. 补齐真实企业场景下的权限、运营、监控和治理能力。

目前项目更像是一个 **RAG 技术平台 Demo**，还不是一个完整的 **知识问答产品**。

---

## 1. 当前项目优势

从 README 和现有前后端结构看，项目已经具备以下基础能力：

- **Agentic RAG 问答**：通过 LangGraph 编排查询分析、向量检索、重排序、上下文构建、答案生成、质量评估等节点。
- **文档管理**：支持上传文件或纯文本，保存文档元数据，并可选择生成向量写入向量库。
- **多格式解析**：支持 PDF、Word、PowerPoint、Excel、TXT、Markdown 等文档类型。
- **多种文本切分策略**：支持 recursive、character、token、semantic、paragraph、sentence。
- **向量存储后端可切换**：支持 Milvus 或 PostgreSQL + pgvector。
- **多租户隔离**：API 和向量数据均支持 tenant_id。
- **OpenAI 兼容模型接入**：LLM、Embedding、Reranker 均通过 OpenAI 兼容接口配置。
- **Gradio 前端**：提供问答、查询分析、文档管理、系统状态四个页面。

这些能力说明项目已经有较好的工程基础，适合作为企业知识库问答、内部文档助手或 RAG 平台原型继续演进。

---

## 2. 产品定位需要进一步收敛

### 2.1 当前问题

项目目前更偏“技术能力展示”，但产品层面还没有回答清楚：

- 它主要服务谁？
- 用户为什么每天要使用它？
- 它替代或增强了用户当前哪一个工作流程？
- 它相比普通 ChatBot 或搜索框的核心优势是什么？

目前的功能描述包括 FastAPI、LangGraph、向量库、Rerank、质量评估等，这些对开发者有吸引力，但对真实业务用户而言，还需要转化成明确的产品价值。

### 2.2 建议定位

建议先收敛成一个主场景：

> 面向企业内部知识库的 AI 问答助手，支持员工上传制度、流程、产品文档，并通过可溯源答案提升查询效率。

围绕这个定位，可以定义四类核心用户：

| 用户角色 | 核心需求 |
|---|---|
| 普通员工 | 快速提问，获得可信答案和出处 |
| 知识管理员 | 上传、更新、删除、管理文档 |
| 业务负责人 | 查看使用效果、命中率、用户反馈和知识缺口 |
| 技术/运维 | 监控模型、向量库、接口、成本、错误日志 |

### 2.3 产品信息架构建议

当前前端包含：

- AgenticRAG 问答；
- 查询分析；
- 文档管理；
- 系统状态。

建议未来调整为：

1. **AI 问答工作台**：面向普通用户；
2. **知识库管理**：面向知识管理员；
3. **质量运营看板**：面向业务负责人；
4. **系统与成本监控**：面向技术/运维；
5. **调试模式**：保留查询分析、检索结果、Rerank 分数等工程信息，但默认对普通用户隐藏。

## 3. P0：最优先改进方向

### 3.1 强化可信答案体验

#### 当前问题

RAG 产品的核心不是“能回答”，而是“用户敢相信”。

当前系统已经有质量分数 `quality_score`，并且在前端展示质量分数。但单一分数对用户来说不够直观，也不足以建立信任。

真实用户会关心：

- 这个答案从哪份文档来的？
- 哪些原文片段支持这个结论？
- 答案有没有可能不准确？
- 如果知识库没有资料，系统会不会编造？
- 我能不能点开原文验证？

#### 改进建议

优先增加以下能力：

1. **答案引用来源**
   - 每个关键结论后显示引用文档；
   - 引用包含文档标题、页码、段落、上传时间；
   - 支持点击打开原文片段。

2. **证据高亮**
   - 在答案旁边展示支持该回答的原文片段；
   - 高亮与答案相关的句子；
   - 支持“查看完整上下文”。

3. **不确定性表达**
   - 不只展示 `0.82` 这种质量分；
   - 转化为用户能理解的提示，例如：
     - 资料充分；
     - 资料较少，建议人工确认；
     - 未找到可靠依据；
     - 当前答案可能不完整。

4. **拒答机制产品化**
   - 当检索结果不足时，明确说明“当前知识库没有足够信息”；
   - 给出下一步建议，例如“请上传相关制度文档”或“尝试换一种问法”；
   - 避免为了回答而回答。

#### 推荐优先级

这是所有改进中最优先的一项。没有引用和溯源，RAG 产品很难在真实业务场景中被信任。

---

### 3.2 文档管理从“上传工具”升级为“知识库管理系统”

#### 当前问题

当前文档管理功能已经支持：

- 文件上传；
- 纯文本上传；
- 文档列表；
- 删除文档；
- 选择切分方式、chunk size、chunk overlap；
- 是否存储向量。

但整体体验仍偏开发者工具，不像真实业务用户使用的知识库系统。

#### 改进建议

##### 1. 文档入库流程可见

上传文档后，不应该只返回“文档上传成功、ID、类型、块数”。

建议展示完整状态：

- 上传中；
- 解析中；
- 切分中；
- 向量化中；
- 入库成功；
- 入库失败；
- 失败原因；
- 支持重试。

##### 2. 文档列表表格化

当前文档列表是纯文本输出。建议升级为表格：

| 文档名 | 类型 | 状态 | 块数 | 上传人 | 更新时间 | 是否已向量化 | 操作 |
|---|---|---|---|---|---|---|---|

同时支持：

- 搜索；
- 按租户筛选；
- 按知识库筛选；
- 按文件类型筛选；
- 查看切片内容；
- 重新向量化；
- 批量删除；
- 批量上传；
- 文档版本管理。

##### 3. 切片参数产品化

当前上传文件时直接暴露 `split_method`、`chunk_size`、`chunk_overlap`。这对开发者有用，但对业务用户过于技术化。

建议改为：

- 默认使用智能切分；
- 高级设置默认折叠；
- 提供业务预设：
  - 通用文档；
  - FAQ；
  - 法规制度；
  - 产品手册；
  - 论文报告；
  - 表格数据。

##### 4. 文案细节优化

当前前端有“存储向量到 Milvus”的文案，但项目支持 Milvus 和 PostgreSQL + pgvector 两种向量后端。

建议改成：

- “生成并存储向量索引”；或
- “存储向量到向量库”。

这可以避免用户误以为系统只支持 Milvus。

### 3.3 建立用户反馈闭环

#### 当前问题

系统现在有质量评估节点，但这是模型自己评估自己。真实产品还需要用户反馈。

没有用户反馈，RAG 产品无法持续变好，也无法判断哪些问题最影响体验。

#### 改进建议

##### 1. 每个回答增加反馈按钮

建议支持：

- 👍 有帮助；
- 👎 没帮助；
- 答案不准确；
- 没有引用来源；
- 遗漏关键信息；
- 回答太长；
- 回答太短；
- 用户补充正确答案。

##### 2. 建立反馈后台

统计以下内容：

- 高频问题；
- 无答案问题；
- 低质量回答；
- 用户差评问题；
- 命中文档最多的知识；
- 长期无人使用的文档；
- 检索失败率；
- 平均响应时间；
- 模型调用成本。

##### 3. 用反馈驱动优化

基于反馈做：

- 补充文档建议；
- 问题聚类；
- FAQ 自动生成；
- 知识缺口分析；
- Prompt 优化；
- 检索参数优化；
- Golden Set 回归测试。

这是从“能答”走向“越用越好”的关键。

---

### 3.4 建立 RAG 评测体系

#### 当前问题

RAG 产品不能只靠人工体验，必须有评测集和可量化指标。

当前系统已有质量评估节点和质量阈值，这是一个起点，但还不是完整评测体系。

#### 建议评测指标

| 指标 | 含义 |
|---|---|
| Recall@K | 相关文档是否被召回 |
| MRR / NDCG | 相关文档排序是否靠前 |
| Faithfulness | 答案是否忠于上下文 |
| Answer Relevance | 答案是否回答了问题 |
| Citation Accuracy | 引用是否真的支持答案 |
| Refusal Accuracy | 不知道时是否正确拒答 |
| Latency | 响应耗时 |
| Cost per Query | 单次问答成本 |
| User Satisfaction | 用户满意度 |

#### 产品化能力建议

- 评测数据集管理；
- 一键评测；
- 版本对比；
- Prompt / 模型 / 切分策略 A/B 测试；
- 每次改动后的回归评估报告；
- 自动生成低分样例；
- 支持人工标注正确答案和相关文档。

---

### 3.5 前端体验从“开发者控制台”升级为“用户工作台”

#### 当前问题

Gradio 前端适合作为 Demo 和内部调试工具，但如果要给真实用户使用，还需要更强的产品体验。

#### 问答页建议

增加：

- 流式输出；
- 引用卡片；
- 历史会话列表；
- 会话重命名；
- 复制答案；
- 导出问答；
- 多轮上下文可视化；
- 用户反馈按钮；
- 推荐追问；
- “仅在某个知识库内搜索”；
- 答案生成过程状态展示。

#### 查询分析页建议

查询分析对开发和调试有价值，但对普通用户价值有限。

建议：

- 默认隐藏；
- 放入“调试模式”；
- 仅管理员或开发者可见；
- 与每次问答详情打通，而不是作为独立主入口。

#### 系统状态页建议

当前系统状态主要展示 API 和 AgenticRAG 是否正常。建议升级为：

- 数据库状态；
- 向量库状态；
- LLM 服务状态；
- Embedding 服务状态；
- Reranker 服务状态；
- 最近错误；
- 平均延迟；
- 今日请求数；
- Token 消耗；
- 成本估算；
- 单租户资源使用。

## 4. P1：中期应该补齐的能力

### 4.1 权限与多租户治理

项目已经支持 tenant_id，但真实产品不应该让用户手动填写 tenant_id。

建议升级为：

- 登录账号；
- 用户自动绑定租户；
- 租户下有多个知识库；
- 知识库权限：可读、可写、可管理；
- 文档级权限；
- 部门级权限；
- 操作审计日志。

需要避免的问题：

- A 部门看到 B 部门文档；
- 用户误填 tenant_id；
- 普通用户删除别人文档；
- 敏感文件上传后无法追踪责任人。

---

### 4.2 显式增加“知识库 Space”概念

当前系统更多围绕 tenant_id 和 document 管理。建议增加 Space / Knowledge Base 概念。

例如：

- 公司制度知识库；
- 产品手册知识库；
- 售后 FAQ 知识库；
- 研发规范知识库；
- 合同模板知识库。

用户提问时可以选择：

- 全部知识库；
- 指定知识库；
- 多个知识库组合搜索。

这比让用户理解 tenant_id、collection、vector backend 更符合产品直觉。

---

### 4.3 增加数据源连接器

当前项目支持上传文件和纯文本，这是第一步。真实业务里的知识通常来自：

- 飞书文档；
- Notion；
- Confluence；
- 企业微信文档；
- Google Drive；
- SharePoint；
- Git 仓库；
- 数据库；
- API；
- 网页；
- FAQ 系统；
- 工单系统。

建议后续增加连接器体系：

| 数据源 | 价值 |
|---|---|
| 网页爬取 | 快速构建公开知识库 |
| Confluence / Notion | 企业知识库接入 |
| GitHub / GitLab | 代码与文档问答 |
| 飞书 / 企业微信 | 国内企业常用 |
| 数据库 | 结构化数据增强问答 |
| 工单系统 | 沉淀客服与运营经验 |

---

### 4.4 成本和性能产品化

RAG 产品上线后，业务和运维会关心：

- 一次问答多少钱？
- 慢在哪里？
- 哪个节点最耗时？
- 是否每次都需要 Rerank？
- 是否可以缓存？
- 是否可以批量 embedding？
- 是否可以降低模型调用次数？

建议增加：

- 每次请求的链路耗时；
- LLM token 统计；
- Embedding 调用次数；
- Reranker 调用次数；
- 缓存命中率；
- 单租户成本统计；
- 慢查询分析；
- 节点级耗时瀑布图。

---

### 4.5 Agentic 过程可解释、可控

项目叫 AgenticRAG，因此应让用户和管理员理解 Agent 到底做了什么。

建议展示：

- 当前正在分析问题；
- 正在生成检索策略；
- 正在检索文档；
- 正在重排序；
- 正在生成答案；
- 正在评估质量；
- 为什么需要二次检索；
- 每轮检索使用了哪些关键词；
- 每轮检索结果有什么变化；
- 最终采用了哪些证据。

这可以提升信任，也能帮助调试和运营。

## 5. P2：后续可以做成亮点的能力

### 5.1 主动知识发现

系统不仅回答用户问题，还可以主动发现：

- 哪些问题经常问但没有答案；
- 哪些文档过期；
- 哪些文档互相矛盾；
- 哪些制度缺少解释；
- 哪些 FAQ 应该被沉淀；
- 哪些文档被大量引用；
- 哪些知识区域无人维护。

这会让产品从“问答工具”升级为“知识运营平台”。

---

### 5.2 个性化回答

根据用户身份调整答案：

- 新员工：解释更详细；
- 老员工：直接给结论；
- 销售：突出客户话术；
- 技术：突出接口、配置、流程；
- 管理者：突出决策摘要。

---

### 5.3 多模态文档理解

当前支持多种文档格式，但可以继续增强：

- 图片 OCR；
- PDF 表格理解；
- PPT 图文关系理解；
- Excel 表格问答；
- 图表解释；
- 扫描件识别；
- 合同版式解析。

企业知识库中，PDF、扫描件和表格质量往往决定产品上限。

---

### 5.4 工作流集成

问答只是入口，后续可以把答案转成动作：

- 根据制度生成审批材料；
- 根据知识库生成邮件回复；
- 根据客服知识生成工单回复；
- 根据产品文档生成培训题；
- 根据会议纪要生成待办；
- 根据合同条款生成风险提示。

## 6. 推荐产品路线图

### 第一阶段：把 Demo 打磨成可用 MVP

目标：让一个小团队可以真实上传文档并稳定问答。

重点：

1. 答案引用与原文溯源；
2. 文档入库状态；
3. 文档列表表格化；
4. 用户反馈按钮；
5. 基础会话管理；
6. 流式回答；
7. 错误提示优化；
8. 隐藏过于技术化的参数。

---

### 第二阶段：变成企业知识库助手

目标：支持部门级、租户级知识库使用。

重点：

1. 登录和权限；
2. 知识库 Space；
3. 文档权限；
4. 多数据源连接器；
5. 管理后台；
6. 使用统计；
7. 问答质量分析；
8. 高频问题和知识缺口分析。

---

### 第三阶段：变成 RAG 运营与评测平台

目标：让团队可以持续优化 RAG 效果。

重点：

1. Golden Set；
2. 自动评测；
3. Prompt / 模型 / 切分策略对比；
4. 检索质量监控；
5. 成本监控；
6. A/B 测试；
7. 自动优化建议；
8. 质量回归报告。

---

## 7. 如果只能马上做 5 件事

建议优先做：

1. **答案引用与原文溯源**
   - 没有引用，RAG 产品很难被信任。

2. **文档入库状态与失败重试**
   - 上传后用户必须知道文档到底有没有进入知识库。

3. **用户反馈闭环**
   - 每个回答都要能被评价，差评要能进入改进池。

4. **知识库 Space 概念**
   - 不要让普通用户理解 tenant_id、collection、vector backend。

5. **评测集与质量看板**
   - 否则每次改 Prompt、模型、切分策略，都不知道效果是变好还是变差。

---

## 8. 总结

AgenticRAG 的技术骨架是有潜力的，已经不只是一个简单 RAG Demo，而是具备了 Agent 编排、多租户、文档解析、向量后端可切换、Rerank 和质量评估等基础能力。

但从 AI 产品经理角度看，下一步重点不是继续堆更多模型能力，而是把它从：

> 技术可运行

升级为：

> 用户可信、管理员可运营、效果可评估、企业可治理。

推荐的产品方向是：

> 企业知识库 AI 问答助手 + RAG 质量运营平台。

先做好可信问答和文档管理，再逐步扩展评测、反馈、权限、数据源连接器和运营分析。
